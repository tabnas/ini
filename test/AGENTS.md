# Agents Guide — shared spec fixtures

`spec/*.tsv` holds the cross-runtime conformance fixtures. All three
runtimes run the same files, so a change here affects TypeScript, Go and
Rust together — edit with that in mind.

## Format

Tab-separated, one case per line, with a header row naming the columns
(`input` `expected`). Blank lines are skipped.

| Column | Meaning |
|---|---|
| `input` | INI source. |
| `expected` | The parse result as JSON, or an `ERROR:`-prefixed cell for input that must be rejected. |

### What the loaders actually do — mind these

- **Escapes are the shared codec's**, from `@tabnas/support`: `\n`, `\r`,
  `\t` and `\\` are decoded, and every other backslash sequence survives
  verbatim — which is how `sections-escaped-dots.tsv` writes `[C:\path]`.
  Only the `input` column is decoded. The `expected` column is raw JSON,
  which carries its own escape rules and must not be decoded twice.

  Both of those changed when this repo moved onto the shared loader. Its
  own loader decoded *every* column, and did not treat `\\` as an escaped
  backslash — so `\\n` meant a backslash followed by a newline. To say
  that now, write `\\\n`: the 14 cells that relied on the old reading
  were re-encoded, by decoding them the old way and re-encoding them with
  the shared codec, so every one still means exactly what it meant.
- **`ERROR:<code>` pins the error's `code`, exactly.** Both runners read
  the text after the colon and compare it against the code the parser
  answers with — the shared runner's default behaviour, with no
  per-runtime hook in between. The two codes the fixtures use,
  `duplicate_section` and `unterminated_section`, are declared in
  `ini-grammar.jsonic` and raised by every runtime. Message wording is
  deliberately **not** pinned: it is not a cross-runtime contract, and it
  may be reworded. A new rejection therefore needs a genuinely declared
  code, not a symbolic name resolved through message matching — which is
  what the runners used to do, via hand-synced regex tables that have
  since been deleted.
- **A line with no tab is a failure in every runtime**, named by file and
  line. It used to be silently dropped by Go and to crash TypeScript on
  `undefined.startsWith`. Every runner asks the shared loader for
  `minCols: 2`, which is what keeps that true. The one softening: a
  `#`-leading line with no tab is a comment to the shared loader and is
  skipped before the check rather than rejected. There are none in these
  fixtures, and a `#`-leading line WITH a tab is still data — which is
  what `line-comments.tsv` needs.
- **A fixture that loads zero cases fails.** An emptied, renamed or
  header-only `.tsv` used to pass green in both runtimes then, because the loop
  over its rows simply never ran.

The docs should follow the code, not lead it.

## The third-party conformance corpus

Separate from these fixtures, `ts/test/conformance.test.ts`,
`go/ini_conformance_test.go` and `rs/tests/conformance_test.rs` run a
corpus of third-party INI documents from four upstream implementations,
pinned to commit SHAs. INI has no
authoritative conformance suite; the assembled manifest
`corpus/ini-corpus.json` is committed and self-contained (sources,
per-document SHA-256, oracle values, upstream SHAs), so all three suites
run with no network and **fail rather than skip** when it is absent.

Twelve of the thirty valid documents read differently from the oracle,
each for a documented dialect reason, so the oracle cannot say whether a
runtime read them correctly. `corpus/ini-canonical.json` records what the
canonical TypeScript makes of those twelve, and all three suites compare
against it exactly; its key set is asserted to be the divergence list.
It is generated by `scripts/build-ini-canonical.js` from a built `ts/`.

The manifest is generated by `scripts/build-ini-corpus.js`, driven by
`scripts/fetch-ini-corpus.sh`, which clones each upstream at its pinned SHA
into the gitignored `corpus/upstream/`. Those scripts are a regeneration
and audit tool, not a test prerequisite — nothing in the test path runs
them. Read the header of `scripts/build-ini-corpus.js` for the provenance
of every document, label and expected value, and for what the numbers do
and do not prove.

## Who runs what

- TypeScript: `ts/test/ini-tsv.test.ts` — a `makeRunner(...)` per fixture.
- Go: `go/ini_tsv_test.go` — a `support.Runner{...}` per fixture.
- Rust: `rs/tests/parity_test.rs` — a `tabnas_support::Runner` per
  fixture, with the option table in `rs/tests/common/mod.rs`. It also
  names every fixture, so a renamed or deleted `.tsv` is a failure
  rather than quietly reduced coverage.

All three hold only what is specific to ini: the per-file option table and
the message table above. Everything else — finding `test/spec`, reading the
file, decoding escapes, the comparison, the `<file>:<line>` in a failure
message — comes from [`@tabnas/support`](https://github.com/tabnas/support)
and its Go and Rust halves, so the three loaders cannot drift from each
other either.

Fixtures are discovered by **listing the directory**, not by being named in
a test. A new `.tsv` therefore runs in all three runtimes at once, with the
default options; add an entry to the option table only if it needs
something else.

## Rules

- Prefer adding a fixture here over a one-off in-language assertion when a
  case is expressible as input → output. That is what keeps the three
  runtimes honest against each other.
- TypeScript is canonical. If the runtimes disagree, the TS behaviour is
  the expected value — unless Go has exposed a genuine TS defect, or the
  difference is one of the intentional divergences the root `AGENTS.md`
  records, which stay out of these shared fixtures.
- A new fixture must pass in ALL THREE runtimes before it counts:
  `go test ./...` from `go/`, `cargo test --all-targets` from `rs/`, and
  **`npm run build && npm test`** from `ts/`.
  Plain `npm test` runs the previously compiled `dist-test/`, so it can pass
  without ever loading a newly added fixture.
